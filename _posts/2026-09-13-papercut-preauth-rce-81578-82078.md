On September 10, PaperCut published maintenance releases 26.0.5, 25.0.13, and 24.1.10 to close a pre-authentication remote code execution chain in PaperCut NG and MF.

That should be the comforting part of this story. It is not.

A day earlier, [GreyNoise reported](https://www.greynoise.io/blog/ai-orchestrated-campaign-against-papercut-ng-mf) that one actor had already compromised at least 440 PaperCut instances belonging to 395 identified organizations across 48 countries. Among those observed instances, it recorded credential harvesting in 280, operating-system or domain-secret access in 147, and domain-administrator access in 12 victim environments. During the full campaign, 11 organizations were compromised in 26 seconds. One American high school went from initial access to domain admin in seven minutes.

The two bugs are ordinary in the worst possible way. CVE-2026-81578 asks the wrong object whether a request is authorized. CVE-2026-82078 lets configuration choose a Java driver class without an allowlist. The first bug gives an unauthenticated attacker the configuration access required by the second. Together they turn a public management interface into code execution inside the PaperCut server process.

AI did not create either mistake. It changed the clock around them.

One boundary before going further: PaperCut is proprietary, and I do not have its source. I did not reproduce this exploit against PaperCut. This is a report-only assessment based on [PaperCut's advisory](https://www.papercut.com/kb/Main/security-bulletin-27-aug-2026-urgent-security-advisory/) and incident account, plus the independent work published by GreyNoise, Huntress, and Rapid7. The Python below is a harmless local control-flow model. It contains no PaperCut endpoints, SQL, class bytes, or deployable exploit logic.

## The chain at a glance

The chain is easier to understand as two trust failures handing control to each other:

```text
ATTACKER (no account)
        |
        v
1. Request displays a public page
   while dispatching an administrative component
        |
        v
2. Authorization follows the displayed page,
   not the component performing the action
        |
        v
3. Attacker changes trusted database-lookup configuration
        |
        v
4. Configuration selects a Java driver class
   with no approved-driver allowlist
        |
        v
5. Attacker-controlled Java bytecode is instantiated
        |
        v
6. Code execution as the PaperCut server process
```

PaperCut assigns [CVE-2026-81578](https://www.papercut.com/kb/Main/security-bulletin-27-aug-2026-urgent-security-advisory/) a CVSS v4.0 score of 8.8, High, and classifies it as CWE-306: missing authentication for a critical function. Its direct impact is unauthorized modification of system configuration.

CVE-2026-82078 scores 9.4, Critical, under CWE-470: externally controlled input selecting code or classes. Its direct impact is arbitrary Java bytecode executing under the PaperCut server process when an attacker can already manipulate the relevant configuration.

There is no honest composite CVSS score to invent for the pair. The important fact is simpler: the first CVE supplies the privilege required by the second, producing pre-authentication RCE. [CISA added both vulnerabilities to its Known Exploited Vulnerabilities catalog](https://www.cisa.gov/news-events/alerts/2026/08/31/cisa-adds-two-known-exploited-vulnerabilities-catalog) on August 31.

PaperCut initially treated all versions of PaperCut NG and MF as potentially affected. The fixed branch floors are 24.1.10, 25.0.13, and 26.0.5. No fixed build is available for version 23 or earlier, so those installations need a major-version upgrade.

The vendor explicitly excludes PaperCut Hive and Pocket, Mobility Print, Print Deploy server components, and client software from the affected scope. Site Servers and secondary or print servers do require the relevant update.

## Bug one: the public page lends its trust to an admin action

The first bug is an authorization check attached to the wrong side of a request.

Huntress describes a PaperCut request as being able to identify one page for the response and a different page that owns the component being executed. Those should be separate security decisions. A public page may be safe to render anonymously. An administrative component that changes server configuration is not safe to invoke anonymously merely because its output appears inside that page.

In the vulnerable path, PaperCut could validate access to the rendered page and miss the stricter permission required by the dispatched component. An attacker selected a public page for the first object and an administrative configuration action for the second. The check saw something public. The server executed something privileged.

That is CVE-2026-81578 in plain language: the application asked the public wrapper whether the request was allowed instead of asking the administrative action that was actually about to run.

[Huntress reproduced a complete pre-authentication configuration takeover and RCE chain](https://www.huntress.com/blog/papercut-actively-exploited) against a stock PaperCut NG 25.0.11.75758 installation. [Rapid7's reconstruction](https://www.rapid7.com/blog/post/etr-papercut-ng-mf-critical-zero-day-exploited-in-the-wild/) independently describes the same wrong-object authorization problem and reports that an alternate public page could bypass the first emergency mitigation.

On its own, this bug changes trusted configuration. That is already serious, but it is the next feature that turns configuration control into process control.

## Bug two: "database driver" means attacker-chosen Java

PaperCut supports looking up card or identity numbers in an external database. That requires a database URL, lookup behavior, and a Java Database Connectivity driver.

Loading a driver by name is normal Java extensibility. Loading whatever class name appears in configuration without checking it against a small set of approved drivers is not.

PaperCut's description of CVE-2026-82078 says its database utilities instantiate configured driver classes without an allowlist. If an attacker can manipulate those parameters, Java bytecode already placed on the application's classpath can be loaded under the security context of the PaperCut process.

The privilege requirement explains why the bug scores 9.4 rather than behaving like a standalone unauthenticated RCE. The driver loader assumes that only a trusted administrator can choose its inputs.

CVE-2026-81578 destroys that assumption.

PaperCut's own [behind-the-scenes account](https://www.papercut.com/blog/news/behind-the-scenes-august-security-incident/) describes attackers combining the rarely used database lookup feature with file-writing behavior and Java class loading to place and execute a payload. The company has deliberately withheld the full chain while exposed systems remain at risk. That is a reasonable boundary, and there is no need to fill the proprietary gaps with invented source code.

The security rule is still clear. Administrative configuration should require authorization at the action being invoked, and a database-driver field should select from approved implementations rather than function as a general class loader. Either control breaks the chain. The vulnerable product lost both.

## The PoC, honestly

The following model demonstrates only the control-flow mistake. It does not import classes dynamically, touch the network, write a file, speak JDBC, or contain a PaperCut route or parameter.

Two local classes exist in a dictionary. One is approved. The other writes a harmless marker into memory. The vulnerable dispatcher authorizes the displayed page instead of the component being invoked, and the vulnerable loader accepts any class in the local dictionary. The model's fixed variants authorize the component and enforce an allowlist; they illustrate the two security invariants without claiming to reproduce PaperCut's undisclosed implementation.

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Page:
    public: bool


@dataclass(frozen=True)
class Component:
    admin_only: bool


PUBLIC_PAGE = Page(public=True)
ADMIN_COMPONENT = Component(admin_only=True)

state = {
    "driver": "ApprovedDriver",
    "marker": None,
}


class ApprovedDriver:
    def start(self):
        pass


class HarmlessMarkerDriver:
    def start(self):
        state["marker"] = "local-control-flow-only"


LOCAL_CLASSES = {
    "ApprovedDriver": ApprovedDriver,
    "HarmlessMarkerDriver": HarmlessMarkerDriver,
}

APPROVED_DRIVERS = {
    "ApprovedDriver": ApprovedDriver,
}


def edit_configuration(params):
    state["driver"] = params["driver"]


def vulnerable_dispatch(displayed_page, component, authenticated, action, params):
    # Wrong object: authorization follows the page being displayed.
    if not displayed_page.public and not authenticated:
        raise PermissionError("authentication required")

    action(params)


def fixed_dispatch(displayed_page, component, authenticated, action, params):
    # Right object: the invoked component enforces its own requirement.
    if component.admin_only and not authenticated:
        raise PermissionError("administrative component rejected the request")

    action(params)


def vulnerable_load_driver():
    # Local dictionary only. No import, reflection, file access, or bytecode.
    driver_class = LOCAL_CLASSES[state["driver"]]
    driver_class().start()


def fixed_load_driver():
    driver_name = state["driver"]

    if driver_name not in APPROVED_DRIVERS:
        raise ValueError("driver is not approved")

    APPROVED_DRIVERS[driver_name]().start()


# Vulnerable model: an anonymous request changes privileged configuration.
vulnerable_dispatch(
    displayed_page=PUBLIC_PAGE,
    component=ADMIN_COMPONENT,
    authenticated=False,
    action=edit_configuration,
    params={"driver": "HarmlessMarkerDriver"},
)
vulnerable_load_driver()
assert state["marker"] == "local-control-flow-only"


# Fixed authorization control: the same anonymous request is rejected.
state.update(driver="ApprovedDriver", marker=None)

try:
    fixed_dispatch(
        displayed_page=PUBLIC_PAGE,
        component=ADMIN_COMPONENT,
        authenticated=False,
        action=edit_configuration,
        params={"driver": "HarmlessMarkerDriver"},
    )
except PermissionError:
    pass

assert state["driver"] == "ApprovedDriver"


# Fixed loader control: even poisoned configuration cannot select that class.
state["driver"] = "HarmlessMarkerDriver"

try:
    fixed_load_driver()
except ValueError:
    pass

assert state["marker"] is None
```

This model was run locally with Python 3 and exited silently with status 0 because every assertion passed. The first assertion shows the two vulnerable decisions combining. The later assertions are negative controls showing that either component-level authorization or driver allowlisting stops the marker from being reached.

That is all this model proves. It is not evidence that I reproduced PaperCut, and it cannot be pointed at a PaperCut server.

## AI is the clock, not the bug

The PaperCut campaign is going to be remembered as an AI attack, which is true and still manages to miss the useful part.

[GreyNoise reports](https://www.greynoise.io/blog/ai-orchestrated-campaign-against-papercut-ng-mf) that a likely Russian-speaking actor used hundreds of AI agents, a Codex harness with a DeepSeek model, a self-built PaperCut and Active Directory lab, an internet-scanning service, and a library of public offensive tools. Work that normally happens in sequence could happen in parallel: build the lab, develop the chain, assemble targets, test post-exploitation, adapt failures, and launch new workers.

According to GreyNoise's telemetry, the actor went from an empty workspace to RCE against a real victim in under four hours, then reached its first domain administrator about two hours later. Once the larger campaign launched, it compromised at least 11 organizations in 26 seconds. The high-school intrusion reached domain admin in seven minutes.

That does not mean every victim became a domain compromise. GreyNoise observed domain-admin access at 12 of 440 instances, and some victims received no immediate follow-up. The 440 is an observed lower bound from one investigation, not a census of every exposed PaperCut server.

It is still enough to break the normal mental model of patching.

These bug classes are old. Internet scanning and credential dumping are old. AI made the feedback loop cheap enough to run at the speed of a job queue.

AI is not the bug. AI is the clock.

## Three emergency releases and a shrinking margin for error

PaperCut received the first report from an education customer at 9:42 a.m. AEST on August 27. Logs showed real code execution rather than exploitation of an already known bug, and the company declared a P0 incident that day.

The first emergency patch shipped early on August 28 for versions 25 and 26, with version 24 following later. It was built to break the known path quickly. Rapid7 subsequently documented that the first mitigation could be bypassed by selecting another public page for the authorization decision.

Release 2 added hardening. Release 3 arrived on September 1 with more hardening and fixes for SAML login and legacy SQL-driver regressions discovered during the emergency sequence. PaperCut now says releases 1 and 2 are not sufficient. Release 3 protects against the disclosed chain, but the company recommends moving every installation to the fully tested September 10 maintenance releases.

This is the part where "why hasn't anyone fixed it?" needs an honest answer: they have fixed the vulnerable code.

PaperCut's public account describes a chain spanning page dispatch, authorization, a rarely used database feature, file placement, and Java class loading. The company was simultaneously identifying variants, backporting mitigations across three maintained version lines, and repairing SAML and legacy SQL-driver regressions. Its normal testing also includes manual work with real printer hardware, which the emergency releases necessarily compressed.

[PaperCut says](https://www.papercut.com/blog/news/behind-the-scenes-august-security-incident/) it chose useful protection immediately over waiting for one perfect, fully tested answer while customers remained exposed. That made the response messy. Incident response is messy.

The September 10 builds are the clean answer for the code. They are not the clean answer for machines reached before them.

## The patch closes the door. It does not empty the building

PaperCut says publicly reachable, unpatched servers are still being targeted, and the second wave of post-compromise activity has become more sophisticated.

PaperCut says the September 10 maintenance releases address the disclosed chain. Installing one does not erase a payload already executed as the PaperCut service. It does not restore a deleted log, revoke a copied password, rotate a domain credential, remove a persistence mechanism, or undo an account added to Domain Admins.

GreyNoise observed attackers harvesting process memory and registry secrets, stealing credentials, deploying tunnels, and using compromised service privileges to move into Active Directory. Huntress observed PaperCut's process launching system-discovery commands and recovered an attacker-supplied Java class designed to execute commands and remove its working files afterward.

PaperCut's indicators reflect that cleanup behavior. Administrators should investigate suspicious child processes from `pc-app.exe` or `pc-app`, missing or truncated `server.log` files, unexpected Java classes under the server library directory, matching command or output artifacts in content storage, and database-lookup errors that do not belong in the environment. The absence of those files is not an all-clear; PaperCut explicitly warns that attackers may delete them as they progress.

Preserve off-host evidence. [Huntress recommends](https://www.huntress.com/blog/papercut-actively-exploited) collecting the PaperCut log directory and configuration, endpoint process trees, file metadata, reverse-proxy and WAF records, firewall and DNS telemetry, network flows, and recent services, tasks, autoruns, and file creation. An attacker can remove a local log. They cannot as easily reach every upstream system that recorded the connection.

Most importantly, PaperCut's recovery guidance is not "patch and scan." If compromise is suspected, the vendor recommends securing current backups, completely wiping and rebuilding the Application Server, and restoring a known-clean backup from before the suspicious activity.

That is the difference between vulnerability management and incident response. The patch repairs software. The rebuild removes the attacker's claim on the machine.

## What to do tonight

If PaperCut NG or MF exists in your environment, the order matters:

1. **Inventory every server.** Include the primary Application Server, Site Servers, and secondary or print servers. PaperCut says the server components need to be updated, not only the primary node.

2. **Remove public exposure.** Restrict the management interface to trusted addresses, a VPN, or another controlled administrative path. For version 23 and older, this is essential while planning the mandatory upgrade to a supported branch.

3. **Install the real maintenance release.** The fixed floors for this disclosed chain are 24.1.10, 25.0.13, and 26.0.5. Emergency releases 1 and 2 are obsolete. Release 3 contains the disclosed protection, but PaperCut still recommends the maintenance build with full QA and additional hardening.

4. **Preserve evidence before restarting or upgrading a suspicious host.** Copy logs and metadata, export endpoint telemetry, and secure proxy, firewall, DNS, identity, and network records somewhere the server cannot alter.

5. **Treat exposure plus suspicious evidence as an intrusion.** Isolate the host, activate the incident-response plan, and follow [PaperCut's wipe-and-rebuild guidance](https://www.papercut.com/kb/Main/security-bulletin-27-aug-2026-urgent-security-advisory/). Restore only from a backup known to predate the activity.

6. **Rotate what the service could reach.** PaperCut credentials are only the beginning. Investigate service accounts, local and domain secrets, database credentials, API keys, newly created accounts, directory changes, and domain-controller activity. GreyNoise's campaign proves that domain access was a real outcome, not a theoretical ceiling.

Do not let a clean vulnerability scan overrule intrusion evidence. A rebuilt, patched server is a recovery. A patched server with yesterday's attacker still inside it is a quieter compromise.

## The seven-minute incident

The lesson here is not that AI suddenly invented a new category of vulnerability. It is that our patch timelines are still measured in maintenance windows while an attacker can now parallelize the work between disclosure, reproduction, targeting, and exploitation.

That makes exposure inventory, network isolation, off-host telemetry, credential rotation, and rehearsed rebuilding part of the patch plan. They are no longer the work that starts after patching fails.

The September 10 update fixes PaperCut. It does not fix the seven minutes before it.
